# dsh-file-outline

给智能体一张**文件地图**，而不是更快的搜索。

> **平台：仅 Windows。** 代码本身不含平台分支，但只在 Windows 11 + DSH 0.2.2-rc.3 上实测过。macOS 与 Linux 未经验证，请勿假定可用。

## 这个插件解决什么

智能体面对大文件时的真实处境不是"搜得慢"，而是**没有坐标系**：`read` 只能从某个位置往后读 2000 行，而"该从哪读"这个判断它自己给不出来；`grep` 要求先有关键词，而你刚打开一个 14 MB 的文件时，根本没有词可搜。

这个插件在模型决定投入 token 读正文之前，先给它位置信息：这个文件分几个主题、每个主题在哪几行、下一步该读哪一段。

不是搜索加速。实测 ripgrep 扫 14 MB 只要 48 ms，搜索早就够快。

## 什么时候用（适用边界，请先读这一节）

| 文件大小 | 建议 |
|---|---|
| **< 10 KB** | **直接用内置 `read`。本插件在这里是净负担。** |
| 10 KB – 1 MB | 结构不清楚时先 `outline`，否则直接 `read` |
| 1 – 10 MB | 先 `outline`，再 `digest` 取需要的段 |
| > 10 MB | 不要通读。`outline` 定位，`digest` 按段或行号取 |

**只在有结构的文件上有价值。** 对一段无空行、无标题、无行前缀的超大文本，本插件能给的只有行数和编码，那基本等于没有地图。这是定位的边界，不是缺陷。

## 工具

### `file_card`（0.2.0 已实现）

一次调用给出文件的**身份和骨架**，不返回正文：

- **基本信息**：绝对路径、字节数、总行数、编码、最后修改时间
- **规模判定**：量级标签 + 明确建议（小文件直接 read）
- **标题树**：带行号区间，重名折叠
- **首尾样本**：默认各 20 行，**每行硬截 200 字符**，不会因为额度剩余而加长
- **无标题文件的降级导览**：自动改用「按空行分块的段落首句」+「高频行前缀统计」

降级路径的实际效果（对一个真实的 Unity 包日志）：

```
### Structure: no Markdown headings
Paragraph openers (3 of 3 blocks):
  line 2 (1 lines)  === Sat Oct 24 13:32:18 2026
  line 7 (40 lines)  The following packages were added:

Repeated line prefixes (the file's own vocabulary):
  ×31  com.unity.mo
```

时间戳和包名前缀是**自动浮现**的，不需要判断文件类型。

参数：`path`（必填）、`max_headings`（1–1000，默认 200）、`depth`（1–6，默认 3）、`head_lines`（0–100，默认 20）、`tail_lines`（0–100，默认 20）。

### `outline`（0.1.0 已实现）

两种模式：只给路径 → 标题树；给 `keyword` → 关键词的章节归属统计。

模式 B 的要点：

- **单遍扫描**：标题栈和命中计数在同一次遍历完成
- **只给归属统计，不给命中行原文**（那是 grep 的活）
- **全局分布视图**：按文件行数自适应选桶宽（1/2/5 × 10ⁿ），先给出 top 5 桶和全局峰值区间，再列章节。这一步专门用来回答「整体主要集中在哪几万行」
- **按密度推荐「最密的单个章节」，并明确标注它不是全局结论**，且跳过 20 行以下的小段

14 MB 文件实测：807 处命中，158 ms。

为什么要有全局分布：一次 A/B 对照实验中，能调用本插件的模型回答「配色诉求集中在哪」，给出了一个局部高密度章节所在的区间，而全局峰值其实在另一处——因为它只看到了逐章节列表和密度建议，自己没做全局聚合。补上这一行之后，一次调用就能读到：

```
Global distribution (10,000-line buckets, by matching lines):
  lines 140,001–150,000  ████████████ 220 (27.3%)
  lines 110,001–120,000  ██████ 115 (14.3%)
  lines 150,001–160,000  █████ 94 (11.6%)
Overall, the highest concentration is lines 140,001–150,000 (220 of 807 matching lines).
```

参数：`path`（必填）、`keyword`、`literal`、`case_sensitive`、`depth`、`max_items`。

### `digest`（0.3.0 已实现）

按 token 预算取一段，并**明确告知还有多少没返回、下次从哪开始**。

- `section`（章节名，先精确后子串匹配）或 `lines`（`"2100-2600"`）二选一
- `budget`（200–20000，默认 3000）
- 切分**优先在空行边界退让**，不硬切在半句话上；但至少返回 5 行，避免预算过小导致空结果

14 MB 文件实测（budget=800）：

```
Returned lines 119,953–119,976 · 24 lines · ~744 tokens (budget 800)

## 1. 用户明确请求与意图（时间线原文）
1. "UI全部做，做完我再统一检查内容"
...

Not returned: 224 more lines in the requested range.
Continue with digest(path=..., lines="119977-120027", budget=800).
```

**续读指令是它的核心价值**：没有它，这个工具就只是多了一个参数的 `read`。

### token 口径

DSH 核心用 `字符数 / 4`（`CHARS_PER_TOKEN = 4`，from `@deepseek-ai/dsh-token-meter/estimate`）。本插件用**两者取大**：

```
tokens = max(chars / 4,  CJK字符数 × 0.6 + ASCII字符数 × 0.25)
```

理由：`budget` 的目的是防止上下文被撑爆，宁可低估容量也不高估。纯英文/代码文件与 DSH 完全一致；中文文件比 DSH 的进度条更保守（实测差 1.2–1.7 倍）。

## 硬性保证

| 保证 | 如何做到 |
|---|---|
| **零 LLM 调用** | 纯确定性字符串处理 |
| **流式** | `createReadStream` + 自建行迭代器，内存与文件大小无关 |
| **单遍读取** | `file_card` 的结构扫描与首尾样本合并为一次遍历；14 MB 文件从 3 遍降到 1 遍，310 ms → 165 ms |
| **确定性** | 无 Map 迭代顺序依赖、无 locale 格式化、无时间戳进入输出 |
| **只读** | 不写、不删、不改任何文件 |
| **工作区受限** | 路径解析后必须落在 Session 工作目录内，越界直接拒绝 |
| **零运行时依赖** | 只用 Node 内置模块 |
| **输出上限 8000 字符** | 超出时截断并写明原长度 |
| **Windows 平台** | 仅支持 Windows。路径全部走 `node:path`，换行 LF/CRLF/CR 均正确处理，无硬编码路径 |

## 建议搭配

以下插件与本插件互补，但本插件**不依赖**它们：

- 需要按 token 预算精确切块时，配合你已有的预算类工具使用
- 需要正则搜索时，继续用内置搜索工具；本插件只告诉你"命中落在哪一节"，不返回命中行原文

## 测试

九套本地测试，共 **219 项**，全部是纯 Node 进程，不调用任何模型：

| 套件 | 项数 | 覆盖 |
|---|---|---|
| `selftest` | 24 | 围栏、编码、折叠、确定性 |
| `e2e` | 26 | 三工具注册与执行、拒绝路径 |
| `sweep` | 49 | 11 类文本 + 12 项 Markdown 边界 + 3 种编码 + 7 种二进制 + 14 个真实文件 |
| `keyword-test` | 16 | 章节归属、密度排序 |
| `card-test` | 26 | 身份、首尾样本、无标题降级、**单遍读取** |
| `digest-test` | 19 | 预算切分、续读指针、章节定位 |
| `task-simulation` | 15 | **任务级模拟**：把智能体会问的问题变成断言，用独立 oracle 校验答案 |
| `distribution-test` | 14 | 分桶数学与全局分布渲染契约 |
| `portability-test` | 30 | **跨环境**：LF/CRLF/CR、路径隔离、Unicode 与 emoji 文件名、9 种编码、平台差异 |

`task-simulation` 是 A/B 对话实验的替代：不重跑昂贵且噪声大的真实对话，而是让一个**独立于插件计数逻辑**的 oracle 直接从文件算出标准答案，再断言渲染报告里是否含有它。三个工具各自要回答的问题（整体集中在哪 / 分几个主题 / 该读哪段 / 还剩多少）都被覆盖。

运行：`node tools/<name>.mjs --real`（`--real` 会额外跑 14 MB 真实文件）。

## 已知限制

- 只识别 Markdown ATX 标题（`#` 开头）。setext 标题（下划线式）、HTML 块、缩进代码块内的内容不参与解析。
- 编码检测只看前 64 KiB。混合编码文件可能判错。
- **支持的编码**：UTF-8（含 BOM）、UTF-16LE/BE、GBK/GB18030、Big5、Shift-JIS、EUC-KR、Windows-1251（西里尔）、Windows-874（泰文），并以 Windows-1252 / ISO-8859-2 作为西欧/中欧单字节文本的回退。
- **编码判定分两档，不确定时会明说**：
  - `certain`：字节结构足以判定（日文、韩文、俄文、泰文，以及多数中文）
  - `uncertain`：这些字节在多种单字节编码下都合法，无法可靠区分。此时按最可能的一种解码，**并在输出里写明「编码是猜的」**
  
  这不是偷懒。CP1251、CP1252、ISO-8859-2 对同一批字节给出不同但同样合法的字符，单靠解码无法区分——专业检测器需要几 KB 的字节频率表，那会破坏零依赖。**宁可如实报告不确定，也不假装确定。**
- 二进制格式靠魔数识别（PDF/ZIP/OLE2/PNG/JPEG/GIF/ELF/MP4/RIFF）。无魔数且无 NUL 字节的自定义二进制会被当作文本。
- 段落降级的高频前缀只统计前 12 个字符，且数字归一化为 `#`。
